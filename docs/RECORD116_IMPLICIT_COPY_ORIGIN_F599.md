# F599 — two complete 116-byte record copies generated naturally by VC7.1

**Independent pinned original-PE/COFF full-function evidence, not game
source/ownership acceptance.** Original Japanese TH075 1.11 target SHA256:
`bd441e99075436e8dcad26f86ffcf5e6aac4f58b0ed3ee7442e4cb39d8e22c98`.

The two largest R108 unresolved original member-copy functions were not
assumed to be vendor-generated just because older inventory called them
"mixed-member-copy". We decoded the **whole** original native bodies,
including calls, returns and one original EH frame, and tested real
C++ source under the pinned VC7.1 compiler.

## New ordinary C++ reconstruction (785 complete original bytes)

Tracked [`Record116ImplicitCopyF599.cpp`](../probes/Record116ImplicitCopyF599.cpp)
declares a naturally aligned 116-byte record. The first 16-byte field
has a declared nontrivial destructor; ten short fields, two large
scalar fields and other observed scalar members follow at their true
+0x10–+0x40 offsets; the +0x44 region is a naturally copied four-DWORD
member; the +0x54 and +0x64 regions are separate 16-byte nontrivial
members with declared copy constructors, assignments and destructors.
The compiler synthesizes the **record's copy constructor and copy
assignment operator**; no record copy routine is authored in C++.
The original class/type names and semantic meaning of scalar fields
remain unknown. No padding array or fabricated saved temporary was used.

With a freshly compiled `/Od /Ob0 /Gy /GR- /GX /GS /Zi` object, the
independent comparison against the actual original 1.11 EXE gives:

| Entire original function | Original complete instructions | Original CODE | Equal non-COFF CODE | True source COFF operands | Whole linked original CODE |
| --- | ---: | ---: | ---: | ---: | --- |
| `0045AAE0` ordinary copy assignment | 118 | **368** | **360/360** | 2 × `REL32` at `+0x151/+0x163` | **368/368 byte-identical** |
| `004591E0` EH-enabled copy constructor | 128 | **417** | **393/393** | 4 × `DIR32` + 2 × `REL32` | **417/417 byte-identical** |
| **Both original functions** | **246** | **785** | **753/753** | **8**, all individually checked | **785/785** |

The source's two assignment-operator calls resolve to the original
`0045AC50`; the source's two copy-constructor calls resolve to original
`00459390`. For the constructor, the entire native EH preamble,
`00656273` EH handler field and three original `__except_list`
address fields (native zero) are also physically checked. A real
`MOV [EBP-4],0` EH state is emitted after the first nontrivial
16-byte header; a real `MOV BYTE PTR [EBP-4],1` state is emitted after
the first +0x54 member construction; the original state is cleared after
the second member construction. These are generated by member
lifetimes, not hand-written frame assignments.

The verifier individually checks every original target relocation
destination and source COFF offset/type/addend, then **links all eight
actual original fields and compares every original CODE byte**; it
also checks all 118/128 original x86 instruction starts, sizes,
mnemonics, and complete boundaries. It does not silently discard
relocation values or accept a function-sized subrange. No source
byte graft or machine assembly is used.

An explicit negative control compiling the same natural source with
`/GX-` proves that the generated record copy constructor shrinks to
**368 bytes**, losing the original 417-byte EH frame. Ordinary copy
assignment is unchanged at 368 bytes. This is why the actual
**compiler EH switch** and first member destructor matter, not just
layout similarity.

## Remaining original-provenance and exact-adoption limits

This proves that a real **implicit-generated C++ source shape can
produce both entire native functions**, and that the native originals
have matching nontrivial member ownership and call placement. It does
**not** prove the original developer chose implicit rather than an
explicitly authored equivalent, establish the original record type,
or establish the identity of the library/game record owner. A fresh independent scan of **all 4,351 registered whole original
function extents** finds **three direct CALLs to each original
copy worker**, all from independently library-classified wrappers:

| Actual original copy worker | All currently found direct native callers |
| --- | --- |
| `004591E0` copy construction | `00458E70` `std::vector::_Assign_n`; `00459CB0` `std::vector::_Insert_n`; `0045B640` VC7 placement construction |
| `0045AAE0` copy assignment | `0045A950` `std::fill`; `0045AFB0` VC7 non-scalar forward copy; `0045B0C0` `std::_Copy_backward_opt` |

Every direct `CALL` instruction address, its exact destination and the
caller's existing independent library-origin row are checked afresh by
the F599 verifier; a caller added or reclassified later requires a
new review. These are *all discovered registered direct callers*, not
proof of no unregistered/indirect uses, original member class origin,
or implicit-vs-explicit source syntax. A library wrapper can call a
game-defined member, so these observations alone do not prove that
the two nested member-copy implementations were vendor authored.

Therefore **both remain `unknown` in `config/function-origins.csv`**;
`config/functions.csv`, authored/excluded counts, match-unit manifest,
and the 943 exact authored functions/862,726 accepted authored CODE
bytes are unchanged. These two source-shape matches represent **785
source-backed but uncredited original CODE bytes**; the generated
compiler EH handler/unwind sections are not claimed as owned by these
complete original functions or accepted separately. Further work
must independently establish the original record owner, explicit-vs-
implicit syntax provenance and actual member type identities before
changing origin or counting any accepted game CODE.
